## Executive assessment

The application has several useful controls in source: a Vercel CSP and transport/security headers, authenticated AI gateways, server-side image checks, ownership-aware Supabase sync code, and server-side entitlement checks for paid handwriting vision. Local changes add bounded JSON parsing, bucket allowlisting, fail-closed rate-limit behavior, and remove runtime evaluation of workflow JavaScript. The `/documents` path now uses bounded local extraction and a consistent JSON contract; the OCR endpoint enforces a bounded JSON body and image limits. Guest email changes use authenticated `auth.updateUser`, with pending-state recovery, rather than admin-side forced confirmation. A local migration now makes the anonymous quota RPC service-role-only and fixes its parameters.

This is **not** a clean security certification. Production is unchanged; the quota migration has not been applied, the project target still differs from the audited production project, gateway IP-header trust semantics are unverified, generated guest email addresses may be unable to satisfy secure confirmation requirements, and earlier read-only review found public write policies and missing storage limits. Legacy rate limits remain non-atomic, and production-like adversarial testing has not been performed. Source changes remain uncommitted and undeployed.

## Existing controls observed in source

- Vercel config defines HSTS, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, and a Content Security Policy. `src/test/securityHeaders.test.ts` protects selected header expectations.
- `/api/ai` performs server-side Supabase user verification and invokes a quota RPC before chat/probe/model operations; it bounds JSON, messages, prompt lengths, and image payloads. Caller-supplied BYOK headers are distinct from server environment credentials.
- `editor-ai` and `openai-brain` share `requireAIUser`; the helper checks a real Supabase user and fails closed when quota storage is unavailable.
- `handwriting-vision` validates an authenticated user, checks active subscription, bounds image data, and calls `reserve_handwriting_request` before provider work.
- The local image-upload function validates PNG/JPEG/WebP/GIF magic bytes, enforces a decoded-file limit, creates a server-generated path under the authenticated user's ID, and now restricts the service-role bucket.
- The OCR endpoint uses bounded JSON parsing, a 10 MiB image-data limit, and a raster data-URL allowlist; `/documents` additionally limits PDF pages, OCR pages, and extracted text before sending the process request.
- The local cloud-sync changes use owner-scoped notebook/page reads and writes and preserve local data when cloud operations fail.
- The static site CSP and client-env regression test reduce accidental client-side provider-key exposure; they do not protect secrets mistakenly configured as build-time client variables.

## Authentication, authorization, and data boundaries

- A client route being hidden, noindex, or wrapped in a UI component is not a security boundary. Verify authorization in Supabase RLS, server endpoints, and admin role checks.
- Local source contains both direct user-authorized Supabase uploads and service-role Edge Function uploads. Audit both paths and the corresponding storage policies; one validated endpoint does not secure the direct upload path.
- `feature_usage` is user-writable under local policies and should not serve as the authoritative premium/quota ledger. Billing/entitlement decisions must use verified server-side state.
- The local `supabase/config.toml` has `verify_jwt = false` for some functions that implement their own user-token checks. Confirm deployed function settings match the intended code and avoid treating `verify_jwt=false` as a substitute for handler authentication.
- The production and local object/migration inventories differed in the prior read-only review. No remote schema/data writes were performed to investigate the discrepancy.
